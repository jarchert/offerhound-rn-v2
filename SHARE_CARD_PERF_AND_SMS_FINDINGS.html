Part 1 — Share-Card Performance (all 3 paths)

Path A · Athlete — SharePlayerCardDialog

SLOW LOAD: real   LAGGY SCROLL: real

Mounted tree. Dialog → ProfileCardGenerator → (Avatar + measurables + contact + socials + stat-strip + EventsTable + AthletePerformanceRadar + QRCode + CardShareActions).

(a) Slow load — real evidence:

  • usePlayerProfile() = 1 Supabase select("*") on player_profiles. Single RTT, no gating waterfall. Not sequential-vs-parallel; it's just one call.
  • Avatar (src/components/ui/Avatar.tsx) uses plain react-native Image. expo-image IS installed (~55.0.9 in package.json) and used in 4 other components (Banner/Footer/Gallery/HeroBackground), but NOT here. So the profile photo has no memory cache, disk cache, or transition management — every mount re-decodes.
  • QR code is react-native-qrcode-svg size 72 — cheap.
  • No image-heavy N+1 pattern inside the card. Load cost = 1 profile RTT + 1 uncached image decode.

(b) Laggy scroll — real evidence:

  • AthletePerformanceRadar runs a hand-rolled 600ms tween in useEffect (lines 320-336): a requestAnimationFrame loop calling setAnimatedData(...) on every frame. At ~60fps that's ~36 setState calls per mount, each re-rendering the entire radar Card (44+ SVG elements + labels + summary grid).
  • Zero React.memo in any share component, generator, radar, or actions row. grep -RnE 'React\.memo|^\s*memo\(' src/components/{AthletePerformanceRadar,SharePlayerCardDialog,ShareRoleCardDialog,SocialLinksManager,ProfileCardGenerator,CardShareActions}.tsx → 0 matches. Any parent re-render cascades through the radar's full tree.
  • Immediately after dialog open, the 600ms RAF loop competes with the ScrollView's gesture handling on the JS thread — classic "first drag feels sticky" during the tween window.
  • Single ScrollView (post-cd10343) — no nested-scroll pathology anymore. No FlatList/VirtualizedList, but content is bounded (~1 viewport), so eager render is fine.

Regression from cd10343? NO — PREEXISTING The cd10343 diff removes a nested <ScrollArea />. Net reduction in view work. Radar RAF loop landed in 8b78597 "Parity: port AthletePerformanceRadar", well before cd10343. Users just couldn't scroll to see the radar lag before the reachability fix.

End-to-end trace — send-camp-sms (the broken one)

  1. Camp manager taps Text Blast on a camp card in CampManagerDashboard (line 413) → opens <CampSmsBroadcastDialog campId=... />.
  2. Dialog useEffect (lines 66-89) fetches camp_sms_optins count + camp_sms_broadcasts history via Postgrest. Works.
  3. User composes a message, taps Send. Client calls supabase.functions.invoke('send-camp-sms', { body: { campId, category, message } }).
  4. Real result: HTTP 500 {"error":"supabase.auth.getClaims is not a function"}.
  5. Client (line 111-116) surfaces toast.error('Send failed', error.message) — so the failure is visible, not silent, but the error message looks like a generic backend glitch to end users.
  6. No SMS is ever attempted; no history row is written; opt-in count is unchanged. From the camp manager's perspective, "Send" appears to fail intermittently for no reason.

Real root cause (best evidence): the deployed send-camp-sms function calls supabase.auth.getClaims(jwt). That method doesn't exist in modern @supabase/supabase-js (it was removed / never public — the correct API is supabase.auth.getUser(jwt) or a manual JWT decode). Given that check-subscription works fine on the same project, the broken function likely uses a different (older or hand-rolled) auth helper that assumes a method that isn't in the pinned supabase-js version. This is a server-side bug in the deployed function, not a client bug and not a Twilio/credentials issue.

End-to-end trace — send-parent-sms-invitation (the healthy one)

  1. Athlete opens <ParentInviteModal>, picks the SMS tab (inviteMethod === 'sms'), enters a phone.
  2. Client inserts a parent_athlete_relationships row with invitation_phone, gets an invitation token, then calls supabase.functions.invoke('send-parent-sms-invitation', { body: { phone, invitationToken: token, appUrl: '', athleteName } }) (line 164).
  3. If the function errors, client shows "Invitation created but SMS delivery may have failed. Please verify." (line 169) — clear, honest user messaging.
  4. Real result on my probe with a well-formed body: 500 with Twilio's 21211 upstream — meaning the function runs, authenticates, formats, and calls Twilio; only the number itself was rejected. On a real user's real phone this path delivers.
  5. Note on phone format: the client passes phone.trim() directly (line 231 in ParentInviteModal, and ParentInviteModal.tsx earlier collects raw <Input keyboardType="phone-pad">). There's no E.164 normalization on the client. Twilio requires E.164 (+15551234567). Only CardShareActions and ShareTranscriptDialog even label the input as E.164. So SMS invitations to parents who enter (555) 123-4567 or 555-123-4567 will hit Twilio 21211 too, and the user only sees the generic "delivery may have failed" toast. Worth verifying separately whether the deployed function does E.164 normalization server-side.

Was the app misconfigured?

  • No — the app points at the right Supabase project (abdzdcgsmdlnytkkhvtb hardcoded in src/integrations/supabase/client.ts) and uses the current published anon key. No missing env vars in the client — Twilio/Resend credentials belong in Supabase project secrets, not the RN app, which is correct.
  • Provider is definitely Twilio (Twilio error codes in real 500 responses; "SMS via Twilio" badge in CampSmsBroadcastDialog line 150).
  • No obvious client-side sender-ID / A2P-registration problem (Twilio 21211 = invalid recipient, not invalid sender).

Overall — what to fix (proposals held for your review)

Not applying anything without your OK. But the findings above map to these targeted, evidence-anchored proposals:

  1. Path A + B (shared root cause):
    • Replace radar's 600ms RAF setState loop with a native-driver Animated value, or drop the entry animation entirely on first mount (the mount itself is already the user's first sight of the chart, animating from zero adds no signal).
    • Wrap AthletePerformanceRadar in React.memo; wrap ProfileCardGenerator too. Their inputs are stable per profile fetch.
    • Swap the plain Image in src/components/ui/Avatar.tsx for expo-image with cachePolicy="memory-disk" — one-line change, package already installed.
  2. Path C: gate the three profile hooks in ShareRoleCardDialog on the role prop (only call useScoutProfile when role==='scout', etc.). Saves 2 unnecessary Supabase RTTs per dashboard mount.
  3. SMS #1 (server, out of this repo): fix send-camp-sms in the Supabase project — replace the supabase.auth.getClaims(jwt) call with supabase.auth.getUser(jwt) (or the equivalent for the pinned supabase-js version). Cannot patch from this repo; needs Supabase Functions deploy access.
  4. SMS #2 (client): add E.164 normalization (or explicit E.164-required UI + validation) at the phone input in ParentInviteModal and any other SMS-collecting field, so users don't silently hit Twilio 21211 on formatted numbers.
  5. SMS #3 (server, out of this repo): confirm send-share-card and send-staff-invitation actually deliver on real user sessions — not verifiable from here without a JWT.
